# Проверки при недоступном API

Для кандидата `12.1.0.2` был подготовлен автономный этап проверки. Запуск Jellyfin, авторизация, Web Bootstrap и административные маршруты не требуют ключа КиноПоиска. Получение новых карточек из пустого кэша требует настроенного ключа и доступного API.

## Автоматические проверки

Записанные ответы в `KinopoiskApiClientTests` были переведены на `RecordMode.None`. Записи были скопированы в выходной каталог тестов, поэтому их поиск не зависит от текущего рабочего каталога. Сетевой обработчик был заменён обработчиком, запрещающим отправку: отсутствующий ответ приводит к ошибке теста и не дописывает запись.

В `OfflineAcceptanceTests` были соединены настоящие HTTP-клиенты API, кэш и поставщики метаданных Jellyfin. Фиксированные JSON, HTML и HLS возвращаются внутри процесса через `HttpMessageHandler`; обращения к внешним узлам отсутствуют. Производственный адрес API и правила проверки URL сохранены.

| Сценарий | Проверяемый результат |
|---|---|
| Карточка фильма из фиксированного JSON | Название, оригинальное название, описание, жанр, рейтинг, дата премьеры и сохранение Kinopoisk/IMDb/TMDb ID |
| Повторное создание клиентов без ключа | Чтение прежнего дискового кэша без отправки HTTP-запросов |
| Истёкший срок карточки и недоступное получение | Использование прежних метаданных при включённом `UseStaleCacheOnFailure` |
| Сезон и составной эпизод | Разбор ответа API, объединение названий и описаний, дата и повторное чтение дискового кэша |
| Виджет и корректный HLS | Выбор КиноПоиска, сохранение YouTube как резерва, `Referer`/`Origin`, отсутствие API-ключа в запросах к виджету и медиахосту |
| Некорректный HLS | Выбор разрешённого YouTube-резерва и повторное использование оперативного кэша |

В `NativeTrailerPersistenceTests` были добавлены повторная регистрация после удаления дополнительного элемента библиотекой и повторное создание моста с готовым MP4. Сохранение ID, отсутствие дублей и обращений к API проверяются через интерфейсы библиотеки. Эти сценарии моделируют изменение состояния; фактическое сканирование базы Jellyfin и воспроизведение файла проверяются отдельно на сервере.

После однократного восстановления пакетов и сборки тесты выполняются без сервиса КиноПоиска:

```sh
dotnet test src/KinopoiskUnofficialInfo.ApiClient.Tests/KinopoiskUnofficialInfo.ApiClient.Tests.csproj --configuration Release --no-build --no-restore
dotnet test src/Jellyfin.Plugin.Kinopoisk.Tests/Jellyfin.Plugin.Kinopoisk.Tests.csproj --configuration Release --no-build --no-restore
npm run test:web
```

Для первого восстановления NuGet/NPM-пакетов требуется доступ к их реестрам либо заранее заполненный локальный кэш. Ключ КиноПоиска для этих тестов не используется.

## Проверка установленного кандидата

В пакете `kinopoisk-12.1.0.2-systemd.zip` были подготовлены `deploy.py check` и `probe.py`. Первая проверка подтверждает состояние службы, загрузку DLL, Web Bootstrap и анонимный ответ `401`. Интерактивный `probe.py` проверяет вход с современным заголовком `Authorization: MediaBrowser`, capabilities, статус плагина, разграничение административных маршрутов и доступность списка материалов. Проверка ключа КиноПоиска в этот этап не входит.

Из интерактивной консоли контейнера с распакованным пакетом:

```sh
python3 /tmp/kinopoisk-12.1.0.2-systemd/deploy.py check
python3 /tmp/kinopoisk-12.1.0.2-systemd/probe.py
```

Учётные данные Jellyfin вводятся в консоли; пароль скрыт. Созданная сессия закрывается в `finally`. Для администратора ожидаются `modern_authorization=PASS`, `capabilities=PASS` и `admin_routes=PASS`. Для обычного пользователя административные маршруты должны вернуть `403`. Пустая медиатека допустима для этого этапа.

После планового перезапуска Jellyfin обе проверки повторяются. Сохранность Web-интеграции, конфигурации и каталога кэша проверяется до начала обновления метаданных. Не следует очищать кэш для проверки недоступности API: он обеспечивает работу с уже полученными ответами.

## Завершение приёмки

Статус `functional_acceptance=PENDING` был сохранён до фактических проверок. Автономные тесты подтверждают обработку заданных ответов; они не подтверждают действительность ключа, актуальный формат сервиса, доступность изображений и внешних роликов.

После восстановления доступа выполняются получение фильма, сериала, сезона, эпизода и персоны; загрузка изображений и дополнительных блоков карточки; подготовка настоящего трейлера; запуск, звук и перемотка в Web и Android TV. Затем выполняются сканирование, перезапуск и повторный запуск MP4 из кэша с проверкой ID и отсутствия дублей. Отдельно проверяется обновление прежней медиатеки из резервной копии. До завершения этих сценариев кандидат остаётся предварительной сборкой.
